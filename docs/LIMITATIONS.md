# 诚实边界：这份方案做不到什么

写这份文档是为了让任何评审者能在 5 分钟内知道**哪些数字不能用、哪些结论没有**。

---

## 0. 精度准入：**两种口径都过 95%**（单次 95.0720%；重试 96.2851%）

* **单次请求口径（最严格）**：GSM8K 全量 1319 题、并发 8、
  **长样例 5-shot（answer 最长的 5 条示例）+ Thinking Budget 3584**
  = **95.0720%（1254/1319）**，`finish_reason=length` 仅 5 题 ⇒ **达标**。
  两个手段各自只到 94.77% / 94.84%，叠加才过线，原因见 `docs/ACCURACY.md` §4.0。
* **允许重试口径**：标准 5-shot（train 前 5 条）单次 **94.4655%**，对 26 道截断题用四种
  请求参数重试、并集救回 **24/26** ⇒ **96.2851%** ⇒ **达标**，且是两种规则下的最高分。
* **这两个最好成绩不是同一个配置**：单次最佳用「长样例 + TB」，重试最佳用「标准 5-shot +
  重试」。因为 TB 把可重试的截断题提前变成普通题（26→5 条），重试空间被压掉。
  **绝不能写成"单次 95% 且重试 96.29%"**——那是两个配置拼出来的数字。
* 5-shot 相对 0-shot：准确率 **+3.71pp**，截断率 **4.85% → 1.97%**。归因见 §0.1 末段。
* 提取器另修了 4 条真实缺陷（未加括号的 `, or ...` 等价答案尾巴、Unicode 减号 U+2212），
  全量 **+4 题**；只改 `extract_pred`，模型 content 未动。

* **C1 全量 1319 题 = 96.21%**（v6 提取口径；原始末位数字口径 94.9962%，差 1 题）⇒ **达标**。
  **C2 前 300 题 = 95.6667%**（v6，提取修复后）⇒ **达标**。C2 的非截断准确率
  **97.26%**，说明它的算术正确率很高，缺口集中在复读。
* 并发崩塌的根因已修复：`q8_batch2_v6` 的 `batch in (1,2)` 守卫使 bs≥3 的 target verify
  掉回 parent varlen；另有三处 `get_last_loc` int64→int32 步长错位。修复后
  C4/C8 从 **16.7% / 14~16%** 提升到 **92.0% / 91.0%**（v6）。
* **残余限制（诚实说明）**：bs≥3 时约 **2.5%** 的题会撞 `max_tokens` 上限（`finish_reason=length`），
  文本是"猜题目/自我怀疑"死循环。C1 本身也有 0.45%，属 `temperature=0` 贪心解码的固有退化，
  被批量数值微扰抬高。**剔除截断样本后**：C8 前 200 题的非截断准确率 = 92.31%。
* 已穷尽排查、全部无效或有副作用（详见 §0.1）。
* **并发档位梯度（必须一起看）**：C1 全量 1319 = **96.21%**；C2 前 300 = **95.67%**（达标）；
  C4 前 100 = 92.00%；C8 前 200 = 90.00%；**C8 全量 1319 = 90.90%（非截断 94.98%）**。
  也就是说 C1/C2 过线；C4 起会出现
  "同一题在不同 batch 下答案改变"的现象（C1 对 / C8 错共 14 题，详见 §0.1 末段）。
  如果评测按 C8 及以上并发计分，本方案的 GSM8K 端到端不达 95%——但**缺口全部是复读截断**
  （4.85%），对截断题重试可把端到端拉到 93.71%（单策略）或 94.24%（组合），详见 §0.1 表末两行。
* 附带教训：C1 逐位锁只证明**确定性**，不证明**正确性**；早期"放宽 q8 守卫后字节不变"的
  A/B 是在 `get_last_loc` 错位修好**之前**做的，页表错误掩盖了 attention 路径差异。

### 0.1 复读（greedy repetition）排查台账

| 手段 | 结果 |
|---|---|
| `repetition_penalty=1.02` | 与 1.0 **逐字相同**（91.0%）。根因：`dflash_info.py:353-365` 把乘性惩罚施加在**全零缓冲区**上，`where(0<0, 0*s, 0/s)=0` 是恒等 |
| `frequency_penalty=0.3`（修好 cumulate 后）| penalty **确实生效**（判据实验输出分叉），但 GSM8K 仍 91.0% ⇒ 惩罚无法把复读题转成正确题 |
| `presence_penalty=1.0` | 输出格式退化（撞上限），更差 |
| `max_tokens` 2048→4096 | 更差（88.0%），复读更久 |
| `--mamba-track-interval 65536` | 无效（90.0%）|
| `--prefill-max-requests 1` | 无效（C4 18.3%）|
| draft block 独占新页 | 更差（88.0%），浪费 56/64 槽加速驱逐 |
| `--page-size 1` | 该栈图捕获崩溃 |
| `SGLANG_USE_CAUSAL_CONV1D=0` | 服务卡在 import，从未健康 |
| `no_repeat_ngram_size` | 本版本 sglang **无此实现**（全仓 0 处引用，静默丢弃）|
| `--speculative-accept-threshold-*` | 本栈死代码（HIP 早退 + 贪心 argmax），且原理上不改变 target 输出 |
| `--enable-deterministic-inference` | 启动即崩：CUDA graph capture 阶段 GDN `in_proj_ba` 的 fused Triton kernel 报 `OutOfResources: shared memory Required 98304, Hardware limit 65536`。该开关与当前 GDN fuse overlay **不兼容**，不是配置问题 |
| **`max_tokens` 4096→8192（只对 `length` 题重试）** | **有效**：C8 全量 64 道截断题里救回 **43**，端到端 90.45% → **93.71%** |
| **`temperature=0.7, top_p=0.95`（只对 `length` 题重试）** | **有效**：同样救回 **43/64**，与上一行救回的集合不同（交集 36），**并集 50/64**，端到端 **94.24%** |
| 把**默认** `max_tokens` 改成 8192（全量重跑，不重试） | **无效**：同前 300 题对照，8192 救回 7 道截断题但**新弄错 9 道**原本正确的题，净 **+1 题**（92.667% → 93.000%）。重试有效是因为换了生成轨迹，不是 8192 这个数值 |
| **`reasoning_effort=low` / `medium`**（模板原生参数，零侵入） | **能消除复读、但净负**：C8 前 300 题 `length` 从 **12 → 0**，复读彻底消失；但准确率 **92.667% → 91.00%**（low 与 medium 同为 273/300），思考被压到 reasoning 中位数 342/385 字符，推理质量下降的代价大于复读的收益 |
| **修好 DFlash 乘性 penalty 后设 `repetition_penalty`** | **技术上成功、效果净负**：PR78 overlay 让 `repetition_penalty` 第一次真正作用到 verify 的真实 logits（日志 `mulpen applied rp=1.100 hist=N`）。但 `rp=1.05` → 93.00%（相对基线 92.667% 只多 1 题，在 ±3% 噪声内）；`rp=1.10` → **89.667%**，`length` 反而 12 → **14**。过度惩罚破坏正常推理链，比复读损失更大 |
| **句子级重复检测 + 强制闭合 `<think>`（早停）** | **可做但上限不够**：按句子去重率把 26 道截断题分成两类（11 道退化重复 ≥50%、11 道元认知 <20%）。只在"同一句重复 ≥3 次"时强制收束，触发很准，但**答案在首次重复之前就已出现的只有 4 题**，全救回也只到 **94.77%**（+4/1319），仍差 95%，且要承担误杀正常长推理的风险 |
| **`content` 为空时从 `reasoning_content` 回退提取答案** | **不可行**：四种策略（取末尾数字 / 截掉重复段 / 句子去重保序 / 匹配 `answer is`）在 26 题上并集只命中 **5**。原因是**污染不是缺失**——循环里反复重述的题干数字会覆盖前面算对的结论，元认知类还会同时给出两个候选（idx=119 先 `99076.92` 后 `95200`），末尾倾向不稳定 |

**机制层面已证实的两个 DFlash 缺陷（已定位，未全部修）**：

1. `speculative/dflash_info.py:353-365`：乘性惩罚作用在零缓冲 → `repetition_penalty` 恒为 no-op。
2. `managers/schedule_batch.py:2324` 在投机模式提前 return，`cumulate_output_tokens` 被跳过；
   EAGLE 在 `eagle_worker.py:628` 补了，**DFlash 全仓没有** → 所有 penalizer 状态恒为初值。
   已提供 `overlays/` 之外的实验补丁记录（PR76），默认不启用。

**并发档位的精度缺口（未消除）**：对 C1 前 200 与 C8 前 200 逐题对齐，
**C1 对、C8 错共 14 题**（5 题 `length` + 9 题 `stop` 但答案数字改变，
如 idx=20 由 15 变 25）。同一权重、同一贪心解码下答案随 batch 改变，
说明 `bs≥3` 存在 batch 内数值差异（累加顺序/归约顺序），不是评分或提取问题。
`--enable-deterministic-inference` 本可针对该问题，但如上表所示在本栈上无法启动。

**`enable_thinking=false` 口径不可用**：官方套件曾用该口径跑出 8.49%（C8、1319 题），
但复核原始记录后确认这是**口径缺陷**而非模型精度：43.37% 的题目撞满 4096 token 上限，
其中 85.5% 是退化复读；平均延迟 96.66 s，是 thinking 模式（9.04 s）的 10.7 倍；
全量仅 1 条输出含 `\boxed{}`。chat template 对 `enable_thinking=false` 正确注入了空的
`<think>\n\n</think>\n\n` 块，但**模型不遵守**，继续输出无终止条件的长 CoT。
五种提取器取并集的上界只有 9.78%，即 **<15% 的失分可归因于评分，>85% 是模型在该模式下真的没答对**。
因此 8.49% 已从所有交付文档中撤下，真实精度以 thinking 口径的 C1/C2 数据为准。

**复读的根因已定位到"思考失控"，而不是采样参数**：C8 全量里 64 道 `finish_reason=length`
的题，`content` 中位数 **0 字符**（`<think>` 从未闭合），`reasoning_content` 中位数
**15351 字符**；而 1255 道正常题的 reasoning 中位数只有 **401 字符**（p90 = 1593）。
差 38 倍。也就是说复读不是"输出重复某个词"，而是模型在思考阶段陷入
「这是不是题目有问题 / 我是不是幻觉了 / 再读一遍输入」的元认知循环。

这解释了为什么所有采样侧手段都只能缓解、不能根治：

| 手段 | 复读率 | 端到端 | 判断 |
|---|---:|---:|---|
| 基线（xhigh，mt=4096） | 4.85%（全量） | 90.45%（全量） | — |
| `reasoning_effort=low` | **0%** | 91.00%（前 300） | 消除复读，但思考被压扁，净负 |
| `reasoning_effort=medium` | **0%** | 91.00%（前 300） | 同上 |
| 修好乘性 penalty + `rp=1.05` | 3.67% | 93.00%（前 300） | 噪声内 |
| 修好乘性 penalty + `rp=1.10` | 4.67% | **89.67%**（前 300） | 净负，过度惩罚 |
| **对 `length` 题重试（4 策略并集）** | — | **94.77%（全量推算）** | **目前最优** |
| **5-shot CoT（train 前 5 条示例）** | 4.85% → **1.97%** | **94.4655%（全量单次）** | 主结果；同时提准确率与压循环 |
| **5-shot + 对 26 道截断题重试** | — | **96.2851%（全量）** | **达标（24/26 救回）** |
| 5-shot + system 指令（"Think concisely... Do not re-read or question the problem statement."） | 2.05% | 94.5413%（全量单次） | **无效**：比不加 system 高 1 题，在 ±3% 噪声内；前 300 题的 +0.67pp 是小样本波动 |
| **Thinking Budget Soft-Close**（`Q38_THINK_BUDGET=3584`，服务端强制闭合 `<think>`） | **0.15%**（26→2） | **94.8446%（全量单次）** | **部分有效但不足以达标**：截断率从 1.97% 压到 0.15%，净 +5 题，仍差 2 题到 95%；且**与重试策略冲突**（见下） |

**PR78（乘性 penalty 修复）的技术细节**，供后续复用：`dflash_info.py` 的 verify 把
`apply_logits_bias` 作用在全零缓冲上，乘性 `apply_scaling_penalties` 对 0 恒等；
而 `cumulate_output_tokens` 因 `if not self._is_prepared: return` 在 batch 级 prepare
之前被静默跳过（实测 `cumulated` 计数恒为 0、`acc_scaling_penalties` 恒为 ones）。
最终可行的做法是**在 verify 包装里直接从 `batch.reqs[i].output_ids[-512:]` 构造惩罚**，
用 `torch.where(sub<0, sub*rp, sub/rp)` 只改历史 token 那几列（每步几万元素，
而不是 bs×vocab 的 32 MB）。该实现已跑通（`rp=1.100 hist=N` 日志可见），
但因效果净负**默认不启用**。

**5-shot 为什么有效，以及它没解决什么**（前 300 题逐题归因）：

5-shot 救回 19 道、新错 13 道，净 +6。拆开看：

| 来源 | 救回 | 新错 | 净 |
|---|---:|---:|---:|
| 格式/提取（末尾不再写"or 2 hours 40 minutes"这类备选段） | +7 | 0 | **+7** |
| 循环/截断（不再跑飞） | +9 | −3 | **+6** |
| 真实推理 | +3 | −10 | **−7** |

也就是说 **+13 来自"格式与稳定性"，真实推理反而净 −7**——13 道新错里 10 道是
解法被压成短 bullet 导致漏步（把 2×2 当 7、用 +20% 代替 −10%、漏掉营收最后一步）。
`####` 的服从度只有 **52%**，所以收益也不是"提取器变好用"。

**5-shot 并没有消除循环**：它把循环从 12/300（4.0%）压到 4/300（1.33%），
全量 64/1319（4.85%）压到 26/1319（1.97%）。剩下的循环题形态完全一致——
`reasoning_content` 12.9K–17.2K 字符、`content` 全空、内容还是
"I'm hallucinating"、"if they wanted addition, they'd say"、"the actual last user is"。
但按句子去重率再拆，这 26 道其实是**两种不同机制**：11 道是句子级退化重复
（50–99% 的句子是逐字重复，如 idx=174 把同一句说了 246/260 次），11 道是元认知长推理
（重复率 <20%，在"是不是读错了/两个候选选哪个"之间反复权衡）。前者是解码退化，
后者是推理策略问题，**不能用同一个开关解决**——这也是 token 级 `repetition_penalty`
两头都不讨好的原因（见 `docs/ACCURACY.md` §4.2d）。
而 5-shot 真正的贡献是给了格式锚点，使**重试的救回率从 67% 升到 92%**（24/26），
这才是达标的直接原因。

## 1. 并发容量：本栈是 C1–C32 的栈

* 冻结配置 `--max-running-requests 32`，但真正决定同时在跑多少请求的是
  `pp_max_micro_batch_size = cap = mamba_pool // 4 = 64 // 4 = 16`。
* 启动几何实测：`max_running_requests=16`。
* 后果：
  * 官方 4K 矩阵的 **C64 / C128** 与 ShareGPT 的 **C64** 在客户端并发高于服务端容量时，
    请求会**排队**（不是崩溃，也不是 OOM，是容量不足）。
  * 提高 `--max-running-requests` 到 64 **不可行**：本栈在 `mr=64` 下内存池分配失败
    （`pool_configurator.py: RuntimeError: Not enough memory`, `max_total_num_tokens ≤ 0`），
    已在 `mem-fraction 0.83 / 0.90 / 0.95` 三种取值下全部复现失败。
  * 根因是 **mamba 池与 KV 池抢同一份显存预算**，且 `cap = mamba_pool/4`。
* 因此本仓库对 C64/C128 的处理是：**照跑、照报、并注明"服务端容量 < 客户端并发"**。
  这类档位的数字反映的是"本栈在该并发下的真实服务能力"，不是"最优并发配置下的能力"。
* 若比赛要求 6 个 4K 档位都必须由同一个候选提供，请把这一条当作本方案的**明确减分项**，
  而不是用别的栈的数字来补。

## 2. SLA：严格口径下本栈不达标（且这是系统性的）

比赛资料里有两组 SLA 口径，本方案按**更严格**的一组自查：

| 类别 | 严格口径 | 本栈实测（见 `RESULTS_OFFICIAL.md`） |
|---|---|---|
| 4K/1K | TTFT p95 < 3 s，TPOT p95 < 50 ms | TTFT p95 在 C1 达标；**C≥8 起大幅超标**（请求数 = 2×并发，排队被计入 TTFT），TPOT p95 约 27–60 ms |
| 64K/1K | TTFT p95 < 15 s，TPOT p95 < 50 ms | **不达标**（C1 已超 2 倍） |

原因是结构性的：**prefill 与 decode 串行**（"prefill first" + DFLASH 禁用 overlap），
一个 4.4K 请求的 prefill 就要约 1.4 s，而每档 2×并发个请求排在同一对卡上。
这不是本栈的配置问题，换更严格的调度也不会消失。

## 3. 精度门：部分基准在离线环境下无法完成

见 `ACCURACY.md`。要点：

* GSM8K 可在本地缓存上离线跑（`MODELSCOPE_OFFLINE=1`）。
* RealWorldQA / LCB v6 / MathVision 依赖外网数据集或代码执行沙箱；宿主机**无外网**时标记为
  `BLOCKED_OFFLINE`，**不当作通过**，也**不用历史数字冒名顶替**。
* 精度数字绑定"权重 + overlay 栈 + 采样参数"；换任一者都要重跑四项门。

## 4. 未被本仓库证明的东西

1. **没有做过跨机器复现**：全部数据来自同一台 2×K100AI 主机（同一对卡）。
2. **没有做过长期稳定性验证**：没有 24h+ soak、没有内存泄漏曲线。
3. **有一个未复现的服务卡死**（长上下文工具会话触发 GDN chunked-prefill 处看门狗自杀），
   触发条件 UNKNOWN，见 `METHODOLOGY.md` §6.3。
4. **单流"100 t/s 级"数字有口径前提**：它绑定固定 prompt / out_len / cache 状态；
   官方随机 token 口径下的 C1 明显更低（见 `RESULTS_OFFICIAL.md` 的口径说明）。
5. **所有非逐位臂的等价性证据是"决策等价"而不是"数值等价"**：
   FASTHEAD 是 argmax 480/480 一致，CANDHEAD 是 top-16 不变性，
   SPLITKV/ATTNCFG 是 accept + content sha 对照。它们**不保证**逐位一致。
6. **本方案没有把 accept 的 batch 依赖修好**（这是最大的剩余杠杆，需要引擎级改动）。

## 5. 与"官方基线"的口径差异

比赛公布的官方基线（K100_AI / SGLang 0.5.12）是 **stock SGLang 0.5.12**，
不含 W8A8 量化、不含投机解码、不含任何本项目 overlay。

因此本仓库的对比是"**本方案 vs stock 官方基线**"，这是比赛要的口径；
但它**不能**被读成"我们的 overlay 带来了全部提升"——
其中相当一部分来自 W8A8 量化与投机解码这两个"组件级"选择。
本仓库所有表格都把"基线 → 本方案"的绝对数字摆出来，读者可以自行做减法。

## 6. 模型身份：本仓库用的是**官方** Qwen3.8-27B 量化副本

这一点必须明说，因为它曾经是一个真实的风险：

* 本仓库全部数据都在
  `/data/my_models/Qwen/Qwen3.8-27B-SmoothQuant-W8A8-INT8`（`base_model: Qwen/Qwen3.8-27B`，
  `base_model_relation: quantized`，见 `manifests/recipe.yaml`、`manifests/target_weights_sha256.txt`）
  上取得。
* 研发期同一套 overlay 栈曾在另一个权重副本（一个 **abliterated**／去拒答变体）上跑过。
  那个变体**不是**比赛指定的 Qwen3.8-27B，因此：
  * 它的 C1 锁（`b8ed32d9…` / `4a9d60be…`）与本仓库的锁（`9351bc60…` / `ee000f28…`）**不同**，
    不能混用；
  * 它的精度表现（GSM8K 子集 93%）**不能**用来代表本方案；
  * 本仓库**不发布**该变体的任何成绩。
* 迁移到另一个权重副本时，**必须重跑** C1 锁 + 质量门 + 四项精度门；
  引擎级 overlay（调优表、pinned 解、融合核）本身与权重来源无关，但**门限值会变**。
