# 诚实边界：这份方案做不到什么

写这份文档是为了让任何评审者能在 5 分钟内知道**哪些数字不能用、哪些结论没有**。

---

## 0. 头号限制：精度准入不通过（提交前必看）

* 冻结候选在 GSM8K 上只有 **10.4%（n=414）**，远低于最低准入 **95.0**。
* 根因**已定位**：**DFLASH 投机解码路径**损坏 target 输出。同一份权重、同一套调优表，
  **关掉投机后 GSM8K = 93.3%（n=150）**。
* 但**关投机的替代配置也仍差 1.7 个点**（93.3% vs 95.0）⇒ 投机是主因，不是唯一缺口。
* 与优化 overlay 臂无关：臂全开与臂几乎全关，精度同为 ~12%。
* 因此：**本候选的性能数字有效，但不能作为一个"可提交的参赛候选"**。
  完整证据链见 `docs/ACCURACY_INVESTIGATION.md`。
* 附带教训：C1 逐位锁只证明**确定性**，不证明**正确性**。

## 1. 并发容量：本栈是 C1–C32 的栈

* 冻结配置 `--max-running-requests 32`，但真正决定同时在跑多少请求的是
  `pp_max_micro_batch_size = cap = mamba_pool // 4 = 64 // 4 = 16`。
* 启动几何实测：`max_running_requests=16`。
* 后果：
  * 官方 4K 矩阵的 **C64 / C128** 与 ShareGPT 的 **C64** 在客户端并发高于服务端容量时，
    请求会**排队**（不是崩溃，也不是 OOM，是容量不足）。
  * 提高 `--max-running-requests` 到 64 **不可行**：本栈在 `mr=64` 下内存池分配失败
    （`pool_configurator.py: RuntimeError: Not enough memory`, `max_total_num_tokens ≤ 0`），
    已在 `mem-fraction 0.83 / 0.90 / 0.95` 三种取值下全部复现失败。
  * 根因是 **mamba 池与 KV 池抢同一份显存预算**，且 `cap = mamba_pool/4`。
* 因此本仓库对 C64/C128 的处理是：**照跑、照报、并注明"服务端容量 < 客户端并发"**。
  这类档位的数字反映的是"本栈在该并发下的真实服务能力"，不是"最优并发配置下的能力"。
* 若比赛要求 6 个 4K 档位都必须由同一个候选提供，请把这一条当作本方案的**明确减分项**，
  而不是用别的栈的数字来补。

## 2. SLA：严格口径下本栈不达标（且这是系统性的）

比赛资料里有两组 SLA 口径，本方案按**更严格**的一组自查：

| 类别 | 严格口径 | 本栈实测（见 `RESULTS_OFFICIAL.md`） |
|---|---|---|
| 4K/1K | TTFT p95 < 3 s，TPOT p95 < 50 ms | TTFT p95 在 C1 达标；**C≥8 起大幅超标**（请求数 = 2×并发，排队被计入 TTFT），TPOT p95 约 27–60 ms |
| 64K/1K | TTFT p95 < 15 s，TPOT p95 < 50 ms | **不达标**（C1 已超 2 倍） |

原因是结构性的：**prefill 与 decode 串行**（"prefill first" + DFLASH 禁用 overlap），
一个 4.4K 请求的 prefill 就要约 1.4 s，而每档 2×并发个请求排在同一对卡上。
这不是本栈的配置问题，换更严格的调度也不会消失。

## 3. 精度门：部分基准在离线环境下无法完成

见 `ACCURACY.md`。要点：

* GSM8K 可在本地缓存上离线跑（`MODELSCOPE_OFFLINE=1`）。
* RealWorldQA / LCB v6 / MathVision 依赖外网数据集或代码执行沙箱；宿主机**无外网**时标记为
  `BLOCKED_OFFLINE`，**不当作通过**，也**不用历史数字冒名顶替**。
* 精度数字绑定"权重 + overlay 栈 + 采样参数"；换任一者都要重跑四项门。

---

## 4. 未被本仓库证明的东西

1. **没有做过跨机器复现**：全部数据来自同一台 2×K100AI 主机（同一对卡）。
2. **没有做过长期稳定性验证**：没有 24h+ soak、没有内存泄漏曲线。
3. **有一个未复现的服务卡死**（长上下文工具会话触发 GDN chunked-prefill 处看门狗自杀），
   触发条件 UNKNOWN，见 `METHODOLOGY.md` §6.3。
4. **单流"100 t/s 级"数字有口径前提**：它绑定固定 prompt / out_len / cache 状态；
   官方随机 token 口径下的 C1 明显更低（见 `RESULTS_OFFICIAL.md` 的口径说明）。
5. **所有非逐位臂的等价性证据是"决策等价"而不是"数值等价"**：
   FASTHEAD 是 argmax 480/480 一致，CANDHEAD 是 top-16 不变性，
   SPLITKV/ATTNCFG 是 accept + content sha 对照。它们**不保证**逐位一致。
6. **本方案没有把 accept 的 batch 依赖修好**（这是最大的剩余杠杆，需要引擎级改动）。

## 5. 与"官方基线"的口径差异

比赛公布的官方基线（K100_AI / SGLang 0.5.12）是 **stock SGLang 0.5.12**，
不含 W8A8 量化、不含投机解码、不含任何本项目 overlay。

因此本仓库的对比是"**本方案 vs stock 官方基线**"，这是比赛要的口径；
但它**不能**被读成"我们的 overlay 带来了全部提升"——
其中相当一部分来自 W8A8 量化与投机解码这两个"组件级"选择。
本仓库所有表格都把"基线 → 本方案"的绝对数字摆出来，读者可以自行做减法。

## 6. 模型身份：本仓库用的是**官方** Qwen3.8-27B 量化副本

这一点必须明说，因为它曾经是一个真实的风险：

* 本仓库全部数据都在
  `/data/my_models/Qwen/Qwen3.8-27B-SmoothQuant-W8A8-INT8`（`base_model: Qwen/Qwen3.8-27B`，
  `base_model_relation: quantized`，见 `manifests/recipe.yaml`、`manifests/target_weights_sha256.txt`）
  上取得。
* 研发期同一套 overlay 栈曾在另一个权重副本（一个 **abliterated**／去拒答变体）上跑过。
  那个变体**不是**比赛指定的 Qwen3.8-27B，因此：
  * 它的 C1 锁（`b8ed32d9…` / `4a9d60be…`）与本仓库的锁（`9351bc60…` / `ee000f28…`）**不同**，
    不能混用；
  * 它的精度表现（GSM8K 子集 93%）**不能**用来代表本方案；
  * 本仓库**不发布**该变体的任何成绩。
* 迁移到另一个权重副本时，**必须重跑** C1 锁 + 质量门 + 四项精度门；
  引擎级 overlay（调优表、pinned 解、融合核）本身与权重来源无关，但**门限值会变**。
