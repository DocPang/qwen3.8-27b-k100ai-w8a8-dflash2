# 复现性修复记录（2026-10-19）

本文记录一次**按仓库原样复现**的核对结果：成绩本身可以复现（C1 逐位、20 题质量门、
C8 吞吐都对得上），但仓库当时有 6 处打包/配置缺陷，会让"一键复现"在中途失败或
静默退化成另一个栈。以下为逐项修复与验证证据。

复现环境：2 × K100AI（gfx928，HCU4/5），镜像
`harbor.sourcefind.cn:5443/hcu/admin/base/sglang@sha256:878d317d…c3aca68`，
官方 W8A8 权重 + DFlash2 草稿，TP2。

---

## 1. 修复清单

### 1.1 `manifests/SHA256SUMS` 含 2 个未入库的 `.pyc`

* 现象：干净 clone 上 `setup_release.sh` 第 1 步 `sha256sum -c` 只有 **396/398**，
  直接 `die`。
* 根因：`.gitignore` 排除 `*.pyc` / `__pycache__/`，但清单里仍列了两个
  `kernels/ops/speculative/__pycache__/*.pyc`。
* 修复：从清单移除这两行（`.pyc` 由解释器在运行时生成，不属于交付物）。

### 1.2 `gdn_split_fused.py` 未入库

* 现象：启动断言 5 条 MISSING（COMBO2 / GDNFUSE / PREFILL / SPLITKV / TAILSYNC），
  几何变成 `max_total_num_tokens=379136`（应为 166720）。
* 根因：`gdn_fuse_overlay/sitecustomize.py` 与 `combo2_overlay/sitecustomize.py`
  都要 `$EXP/gdn_split_fused.py`，但仓库只带了 `sitecustomize.py`。
* 修复：新增 `overlays/gdn_split_fused.py`，`setup_release.sh` 铺到 `$EXP` 根。

### 1.3 `combo_on.txt` 未入库

* 现象：`combo_overlay` 静默 inert，ATT NCFG 链断。
* 根因：`combo_overlay/sitecustomize.py` 以 `$EXP/combo_on.txt`（内容 `on`）为开关，
  仓库未提供。
* 修复：新增 `overlays/gates/combo_on.txt`，`setup_release.sh` 铺到 `$EXP` 根并校验内容。

### 1.4 宿主父链的 DirectLDS `.so` 路径漂移

* 现象：`[Q38 COMBO2] baseline chain failed: …/gateup/v4/q38_smallm_directlds_fused_gateup_v4.so:
  cannot open shared object file`，随后 FASTHEAD 缺失、V6/V7 全部不装。
* 根因：父链（宿主 `batch2_raw_q8_overlay`）按 `gateup/v4/` 取，实际产物在
  `gateup/parent_compile_v4/`。
* 修复：`setup_release.sh` 新增 4b 步，检测到 `parent_compile_v4/` 时补一个同名软链。
  修复后 **7/7 臂 live**，几何 `167808 / 10.32 GB`（文档 166720 / 10.27 GB，差 0.65%）。

### 1.5 冻结配置把并发修复排除在链外（最关键）

* 现象：按仓库自带的 `scripts/sweep_official.env` 起服务，C8 = **107.49 tok/s**
  （等于"修复前"的 112.15），而 README 宣称 177.87。
* 根因：该配置写 `SWEEP_SITECUSTOMIZE_PREFIX=…/candhead_overlay`，`concurrency_fix_overlay`
  根本不在链上；入口脚本里的默认值（concurrency_fix）又被它 source 的 CFG 覆盖。
* 修复：`scripts/sweep_official.env`、`scripts/sweep.env.frozen`、入口脚本默认值、
  `launch_official_lane.sh` 的 `SGLANG_REQUIRED_SITECUSTOMIZE_PREFIX` 统一为
  `concurrency_fix_overlay`（它内部再链到 candhead → combo2 → …）。
* 修复后：日志出现 `q8 verify widened to batch 1..32` / `q8w ACTIVE batch=16 max=32`，
  C8 = **189.67 tok/s**。

### 1.6 入口脚本的宿主绝对路径与固定端口

* 现象：换机器/并行 lane 时无法启动；离线机上 `tvm_ffi` 卡死。
* 修复：
  * `CFG` 改为 `Q38_SWEEP_CFG` > `$Q38_EXP/sweep_official.env` > 历史路径 的优先级；
    `setup_release.sh` 把仓库内 `sweep_official.env` 按 `$EXP` 重写后铺到 `$EXP`。
  * 端口改为 `SWEEP_PORT` / `SWEEP_NCCL_PORT`（默认 18636 / 29636），launch 自动传入。
  * `run_official_suite_official.sh` / `run_fixed_matrix.sh` / `run_sharegpt.sh` 的
    `BASE` 改为可覆盖（`BASE=... bash ...`），不再写死 18636 / 18580。
  * decord wheel 路径改为 `Q38_DECORD_WHEEL`，缺失只告警（纯文本 lane 不受影响）。
  * `launch_official_lane.sh` 对 `tvmffi_cache` 做 fail-closed 检查
    （离线自建需显式 `Q38_ALLOW_TVMFI_BUILD=1`）。

### 1.7 补回头条数字的原始记录

`docs/RESULTS_OFFICIAL.md` 引用的 `perf_std_in4096_c*` 之前不在仓库里，仓库只有
"修复前"的 `fixed-4k-1k-c*`。本次补入：

* `results/official/perf_std_in4096_c{1,8,16,32,64,128}/`（2 预热 + 3 正式，
  对应 61.81 / 177.87 / 200.80 / 207.31 / 217.88 / 223.00）；
* `results/official/sharegpt-c{1,4,16,32,64}/`（逐请求 jsonl + bench_serving 汇总，
  对应 30.88 / 138.88 / 210.73 / 210.85 / 206.58）。

## 3. 仍未解决

1. **C8 TTFT 差 5×**：吞吐对得上但首 token 延迟明显偏高，怀疑与 prefill 分块/排队口径
   或 PREFILL_GDN 生效程度有关，需单独 profile。
2. **C1 需要按 2+3、每轮 8 请求重测**才能和 61.81 公平比较。
3. **C8 轮间波动大**（125.9–197.5）：2+3 的均值 167.89 落在 177.87 的同一水平带，
   但单轮可差 40%，对外引用时应带轮次区间，不要只报均值。
4. **64K / ShareGPT** 的原始记录仍未入库。
5. **GSM8K 95.07%** 对应的 5-shot 全量原始记录仍未入库（现有 `acc_gsm8k*` 是 0-shot
